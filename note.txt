WHAT THIS SITE IS
  Plain static HTML/CSS/JS served by GitHub Pages from the repository root.
  No build step, no framework, no package manager. Edit a file, commit, done.

TWO SETS OF PAGES
  The site is in two halves, which look different on purpose.

  SET A - the main pages, with the sidebar down the left:
    index.html, academics.html, research.html, teaching.html,
    professional-activities.html
  They offer all four appearance controls: light/dark, colour, typeface,
  style. The sidebar also carries a "More to Explore" button, which is
  the way through to:

  SET B - the second set, with a bar across the top and no sidebar:
    noticeboard.html (the Noticeboard), bio.html, gallery.html, news.html,
    blogs.html, useful-links.html, and announcements.html.
    The first six are the six links IN the bar. Announcements is built exactly
    like them and carries the same bar, but is deliberately NOT one of its
    links: it is reached from the Noticeboard, the home page and the Site Map.
  Each opens with a small line above the title (the "kicker"), the title, and
  then a hairline: the Set B pages carry NO tagline under the title, and the
  line does the separating instead. The Set C pages still have their tagline
  and no line.
  ON A NARROW SCREEN (860px and below) those six pages move their title INTO
  the top bar, in place of "Deep H. Makadiya", and take the kicker, the title
  AND the hairline off the screen, so the page starts straight away. The title is only
  hidden from sight, never removed: screen readers, search engines and the
  site's own search still read it. Each page carries its own title in the bar
  as <span class="tb-page-name">, just before the name; the switch itself is
  in the RESPONSIVE section of pages.css. A new Set B page needs that span
  too, or its bar will go on saying his name on a phone.

  SET C - no bar at all: navigation.html (the Site Map) and 404.html. They
  use the same design, only with a plain "back to the home page" link where
  the bar would be, and they do not load pages.js.
  They use the same colours, typefaces and dark mode, but NOT the five
  styles: those are built around a sidebar these pages do not have. Their
  layout lives in pages.css and their top bar in pages.js.

HOW THE CUSTOMISATION WORKS  (read this before touching CSS or JS)
  The sidebar "Appearance" panel offers four INDEPENDENT axes. Each one is a
  single attribute written on the <html> element and remembered in the
  visitor's browser (localStorage):

    attribute              values                                    storage key
    data-theme    cream gold mocha graphite teal emerald sage
                  dusk indigo plum                                   site-theme
    data-font     classic clean readable bold fancy                 site-font
    data-style    card classic midnight grove contrast               site-style
    data-mode     light | dark | auto  (auto = follow the device)      site-mode
    data-appearance  open  (absent = closed)                  site-appearance

  The five typeface pairs, in picker order, are named for how they read
  rather than for their fonts. Each sets a face for headings and one for
  everything else:
    1 Classic  - Playfair Display over Lora (the pair the site opens with)
    2 Readable - Source Serif over Nunito Sans
    3 Sturdy   - Bitter, one slab serif for everything
    4 Bold     - Archivo over Atkinson Hyperlegible, for visibility
    5 Fancy    - three faces, not two: Rouge Script for your name and the
                 title at the top of a page, Englebert for every other
                 heading, and IBM Plex Sans KR for the text. Both scripts
                 come in one weight, so this pair sets
                 font-synthesis-weight:none (which stops the browser faking a
                 bold script) and its own heading sizes
  The name is what the circle shows on hover. Change a pair in the TYPEFACES
  section of styles.css, and add its families to the <link> in EVERY page's
  <head> or it will quietly fall back to Georgia.

  The five styles, in picker order: 1 Classic, 2 Midnight, 3 Parchment,
  4 Sticker, 5 Cards. Those are the names and the order a visitor sees; the
  values stored in data-style never changed, so "grove" is still Parchment,
  "contrast" is still Sticker and "card" is still Cards in the CSS. The
  order lives in the HTML of every page with a sidebar - the CSS blocks stay
  in the order they were written, because the cascade depends on it. Sticker is the bold one - thick
  outlines and a hard accent shadow under anything you can click; its whole
  look is tuned by two variables, --sticker-drop and --sticker-shadow.

  The ten colours are named after their accent alone (Terracotta, Mocha,
  Gold, Sage, Emerald, Teal, Blue, Indigo, Plum, Graphite) and sit in the
  sidebar in palette order: warm, green, blue, plum, then the neutral grey.
  Their data-theme values are unchanged too - Terracotta is still "cream"
  and Blue is still "dusk".

  Plus one attribute the site sets for itself, never the visitor:
    data-panel="dark"  goes on automatically alongside data-style when the
                       style is midnight, grove or contrast. It is what gives
                       those three a dark navigation panel. The list lives in
                       DARK_PANEL_STYLES in script.js and must match the
                       [data-panel="dark"] rules in styles.css.

  How a change actually happens:
    1. A button in the sidebar carries data-set-theme / data-set-font /
       data-set-style. script.js writes the matching attribute on <html> and
       saves the value.
    2. styles.css re-states its CSS custom properties under that attribute,
       e.g. [data-theme="teal"]{ --accent: ...; }. Nothing is hard-coded to a
       colour anywhere else, so one attribute recolours the whole site.
    3. A tiny inline <script> in EVERY page's <head> re-reads localStorage and
       re-applies the attributes BEFORE the page paints, so there is no flash
       of the wrong theme.

  All 4 axes combine freely: any colour x any typeface x any style x light or
  dark must look right. If you add or change one, check the others still work.

THINGS THAT WILL BREAK THE SITE IF YOU GET THEM WRONG
  * 404.html is the ONE page written with plain relative links, so it still
    works when you open it straight from the folder. A one-line script in its
    head adds <base href="/"> only when the browser is on the live site and
    the address sits below the root, which is the only case a plain link would
    resolve wrongly. Do not "tidy" either of those away.
  * Adding a new page: copy an existing page as the starting point. It must
    keep (a) the inline <head> script, (b) the Google Fonts <link>s, (c) the
    whole sidebar block including the Appearance panel, (d) styles.css and
    script.js. Miss the <head> script and the visitor's saved choices are
    ignored on that page only - a confusing bug to chase. Add the new page to
    sitemap.xml too.
  * Adding a colour scheme: add the [data-theme="..."] block in styles.css
    (light) AND its twin under the dark-mode section, then one more button in
    the sidebar of EVERY page. script.js needs no change.
  * Adding a typeface pair: add the font to the Google Fonts <link> on every
    page, add [data-font="..."] in styles.css, add one button per page.
  * Adding a style: add [data-style="..."] rules, one button per page, and if
    it wants a dark panel add its name to DARK_PANEL_STYLES in script.js.
  * Contrast: keep normal text at 4.5:1 or better against its background, in
    BOTH light and dark, for every scheme. The muted grey (--muted) is the one
    that usually fails - check it if you change it.
  * The RESPONSIVE section is the LAST thing in styles.css on purpose. Do not
    add rules after it; a later rule of equal weight would beat the media
    queries and break the phone layout.
  * script.js finds its elements with querySelectorAll, so adding one more
    publication, photo, link, news card or tab is an HTML edit ONLY. If an AI
    proposes editing script.js to add a list item, it has misread the code.
  * Do not introduce a build step, a framework, or npm. The site must stay
    openable by double-clicking an .html file.

HOW THE TWO SETS ARE REACHED FROM EACH OTHER
  * From Set A: the "More to Explore" button under the five menu links goes
    to noticeboard.html, which links on to the rest. The home page also links
    straight to blogs.html, gallery.html and news.html from the "Jump to"
    bar, the photo, and the two "See all ..." links.
  * From Set B: the house at the top left of every page goes back to
    index.html, and the footer repeats the links.
  * Your name is a link home in both halves: in the sidebar, and in the phone
    top bar of the main pages. On a phone that bar also picks up the name of
    the page you are on, in smaller letters after a divider, as soon as the
    in-page tab bar reaches the top of the screen (block 16 of script.js).
    The home page has no tab bar, so it never shows one.
  * THE NOTICEBOARD (noticeboard.html) opens the second set. It says why these
    pages exist, then the announcements that still apply, the newest news and
    the newest posts - each a short list with a link to the full page. The
    announcements live in full on announcements.html; the News page carries
    only news now, and starts straight into its list without a heading of its
    own, since the page is already called News & Updates.
  * ONLY SET C AND THE BLOG POSTS carry a small line above the title. Set B
    pages start with the title itself.
  * THE TWO SET C PAGES are deliberately plain.
      - navigation.html holds five things and nothing else: a panel saying
        what the site is, one section called Site Map (three lists), and the
        "Did you know?", "Like the design?" and "Found a bug?" panels. Each fact there is its own
        paragraph inside the panel; add or drop one and the box re-arranges itself.
        The "Found a bug?" panel carries the same email address as the home
        page; change one and change the other.
      - 404.html holds one section with three buttons - Home, Noticeboard,
        Site Map - and no lists.
  * ANNOUNCEMENTS has two sections of its own: Current Announcements and Past
    Announcements. An announcement that has run its course moves from the
    first into the second rather than being deleted. Each section carries a
    stand-in line while it is empty - "There are no current announcements at
    this time." and "Any past announcements will be displayed here." - with
    the real list kept just below it inside an HTML comment. THE FIRST OF
    THOSE LINES IS ALSO WRITTEN on the Noticeboard and in the home page's
    announcements card; when a real announcement goes up, all three want
    changing.
    The past list carries class "fold-list": script.js then shows its first
    three entries and hides the rest behind a More / Less button, the same one
    the Useful Links page uses. Three entries or fewer and there is no button
    at all, so the list needs no attention as it grows.
  * navigation.html is the SITE MAP - the file keeps its old name so no link
    to it ever breaks, but everywhere a visitor can read it, it is called
    "Site Map". It lists every page of both sets and carries the "Did you
    know?" note that used to sit on the home page. The home page's "Jump to"
    bar links to it, along with five other places.
  * QUOTE OF THE DAY opens the Noticeboard. The words live in quotes.js - one
    line for every day of the year, keyed "MM-DD", 29 February included - and
    that file is loaded by the Noticeboard alone. To change a day, edit its one
    line there; the page itself only holds the frame. Block 6 of pages.js picks
    today's line out. If the date has no line the panel simply does not appear.
  * THE @ BUTTON in the second set's top bar holds "Find me online": LinkedIn,
    GitHub, Google Scholar and ORCID, each with a small mark on the left and
    an arrow on the right to say the link leaves the site. X and Facebook are
    written out directly below them but commented out, waiting for their
    addresses; the comment above them says what to do. The same list is
    repeated in every page of the second set, so a change there is a change in
    ten files.
  * THE FOOT of every page carries one line - "Can't find what you're looking
    for? Try the Site Map." - in place of the row of links it used to hold. The
    Site Map itself is the one page without it.
  * THE SEARCH keeps only the innermost block of text: a list item that holds
    paragraphs is their container, not a line of its own, so a passage is never
    listed twice. A line break counts as a space, or the words on either side
    of it run together in the result.
  * TAGS. Every section of every page may carry data-tags="..." in its opening
    <section> tag - publication, talk, news, photo, award and so on, comma
    separated for more than one. The search reads them, offers them as the row
    of small ovals under the box, and filters by them. Tagging a NEW section is
    one attribute in the HTML and nothing else; the page's own tag (research,
    biography, blog...) comes from the PAGES list in pages.js.
  * DATES are written the same way everywhere they appear: 25 Jul 2026 - day,
    short month, year. Where a day is not known yet an entry carries the month
    and the year alone. The places that hold one are the News page, the
    Announcements page (and its commented-out examples), the two cards on the
    home page, the Latest news and Latest posts lists on the Noticeboard, and
    the Blogs list. A blog post itself carries two: "Posted on" and "Last
    updated on", under its title. The date column is set in small capitals by
    styles.css; that is styling, not the date itself.
  * THE NEWS PAGE, like the Blogs page, has a row of tag buttons above its
    list. Each item carries data-cats with its own tags, space separated - an
    item may hold several (a pre-synopsis seminar is both a milestone and a
    talk) - and each button carries data-filter with one tag, or "all". The
    tags in use are preprint, publication, talk, conference, position and
    milestone. Each item also SHOWS its tags, as small chips at the end of the
    line, drawn by the same rules as the tags on the Blogs page - so a tag must
    be written twice for a new item: once in data-cats, and once as a chip.
    The counts in brackets are typed into the buttons, so update them when the
    list grows. Block 7 of pages.js does the filtering for both pages.
  * SEARCH is on every page now: the button under "More to Explore" in the
    sidebar (a magnifier in the top bar on a phone), and the magnifier in the
    second set's top bar. All of them open the same panel, drawn by
    styles.css and filled by pages.js, which EVERY page now loads - the three
    plain pages included, so that the / key works there too. It reads the pages
    listed in PAGES near the top of the search block in pages.js.
    A result shows the trail it came from (page, then section, then
    sub-section) and carries ?at= and ?find= in its link: the last block of
    pages.js reads those when the page opens, scrolls to that exact line and
    lights up the word, then tidies the address bar. The two places that count
    blocks - the search and the finder - share the BLOCKS selector at the top
    of the search block; if you ever change it, change it once.
    Pressing / opens the search anywhere; typing # in it lists the tags.
    IT ONLY WORKS ON THE LIVE SITE (or any real server): a browser will not
    let one local file read another, so a page opened straight from a folder
    finds nothing and says so in the box. Nothing is broken when that
    happens. THERE IS NO INDEX FILE TO REBUILD -
    it fetches the pages themselves the first time it is used - but a NEW
    page has to be added to that list by hand, or it will not be searched.
  * Blog posts sit one folder down, so their links begin "../". Everything
    else on them is the same as the other Set B pages.

  404.html is built from the Set B design too, and lists every page of both
  sets. It is written differently from every other page on purpose: plain
  relative links, a one-line script that sets <base href="/"> only on the
  live site, and a fallback on each stylesheet and script, so the file also
  works when it is opened straight from a folder. Do not "tidy" that away.
