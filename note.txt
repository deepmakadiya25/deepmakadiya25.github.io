HOW THE CUSTOMISATION WORKS  (read this before touching CSS or JS)
  The sidebar "Appearance" panel offers four INDEPENDENT axes. Each one is a
  single attribute written on the <html> element and remembered in the
  visitor's browser (localStorage):

    attribute              values                                    storage key
    data-theme    cream gold mocha graphite teal emerald sage
                  dusk indigo plum                                   site-theme
    data-font     playfair sourcenunito bitter atkinson cormorant    site-font
    data-style    card classic midnight grove contrast               site-style
    data-mode     dark   (absent = light)                            site-mode
    data-appearance  open  (absent = closed)                  site-appearance

  The five styles, in picker order: 1 Classic, 2 Midnight, 3 Parchment,
  4 Sticker, 5 Cards. Those are the names and the order a visitor sees; the
  values stored in data-style never changed, so "grove" is still Parchment,
  "contrast" is still Sticker and "card" is still Cards in the CSS. The
  order lives in the HTML of every page with a sidebar - the CSS blocks stay
  in the order they were written, because the cascade depends on it. Sticker is the bold one - thick
  outlines and a hard accent shadow under anything you can click; its whole
  look is tuned by two variables, --sticker-drop and --sticker-shadow.

  The ten colours are named after their accent alone (Terracotta, Mocha,
  Gold, Sage, Emerald, Teal, Blue, Indigo, Plum, Graphite) and sit in the
  sidebar in palette order: warm, green, blue, plum, then the neutral grey.
  Their data-theme values are unchanged too - Terracotta is still "cream"
  and Blue is still "dusk".

  Plus one attribute the site sets for itself, never the visitor:
    data-panel="dark"  goes on automatically alongside data-style when the
                       style is midnight, grove or contrast. It is what gives
                       those three a dark navigation panel. The list lives in
                       DARK_PANEL_STYLES in script.js and must match the
                       [data-panel="dark"] rules in styles.css.

  How a change actually happens:
    1. A button in the sidebar carries data-set-theme / data-set-font /
       data-set-style. script.js writes the matching attribute on <html> and
       saves the value.
    2. styles.css re-states its CSS custom properties under that attribute,
       e.g. [data-theme="teal"]{ --accent: ...; }. Nothing is hard-coded to a
       colour anywhere else, so one attribute recolours the whole site.
    3. A tiny inline <script> in EVERY page's <head> re-reads localStorage and
       re-applies the attributes BEFORE the page paints, so there is no flash
       of the wrong theme.

  All 4 axes combine freely: any colour x any typeface x any style x light or
  dark must look right. If you add or change one, check the others still work.

THINGS THAT WILL BREAK THE SITE IF YOU GET THEM WRONG
  * 404.html is the ONE page written with plain relative links, so it still
    works when you open it straight from the folder. A one-line script in its
    head adds <base href="/"> only when the browser is on the live site and
    the address sits below the root, which is the only case a plain link would
    resolve wrongly. Do not "tidy" either of those away.
  * Adding a new page: copy an existing page as the starting point. It must
    keep (a) the inline <head> script, (b) the Google Fonts <link>s, (c) the
    whole sidebar block including the Appearance panel, (d) styles.css and
    script.js. Miss the <head> script and the visitor's saved choices are
    ignored on that page only - a confusing bug to chase. Add the new page to
    sitemap.xml too.
  * Adding a colour scheme: add the [data-theme="..."] block in styles.css
    (light) AND its twin under the dark-mode section, then one more button in
    the sidebar of EVERY page. script.js needs no change.
  * Adding a typeface pair: add the font to the Google Fonts <link> on every
    page, add [data-font="..."] in styles.css, add one button per page.
  * Adding a style: add [data-style="..."] rules, one button per page, and if
    it wants a dark panel add its name to DARK_PANEL_STYLES in script.js.
  * Contrast: keep normal text at 4.5:1 or better against its background, in
    BOTH light and dark, for every scheme. The muted grey (--muted) is the one
    that usually fails - check it if you change it.
  * The RESPONSIVE section is the LAST thing in styles.css on purpose. Do not
    add rules after it; a later rule of equal weight would beat the media
    queries and break the phone layout.
  * script.js finds its elements with querySelectorAll, so adding one more
    publication, photo, link, news card or tab is an HTML edit ONLY. If an AI
    proposes editing script.js to add a list item, it has misread the code.
  * Do not introduce a build step, a framework, or npm. The site must stay
    openable by double-clicking an .html file.

PAGES THAT ARE NOT IN THE MENU
  * blogs.html, gallery.html and news.html carry the sidebar but are left out
    of its six links on purpose. They are reached like this:
      - blogs.html    from the "Jump to:" bar in the "News & Updates" section
                      of the home page
      - gallery.html  by clicking the photo on the home page, and from the
                      "Jump to:" bar
      - news.html     from the two "See all ..." links in the "News & Updates"
                      section of the home page
    If you ever switch the news section off again, news.html becomes
    unreachable from the home page: comment its block out of sitemap.xml and
    put <meta name="robots" content="noindex"> back at the top of it, so an
    orphaned page does not turn up in search.
  * script.js needs NO change either way. It drives the rotating news cards
    from whatever it finds on the page, so with the section absent it does
    nothing.
